# M1 Intern Guide

M1 is the public commerce foundation. It is the first milestone where the site feels like a real public product instead of a scaffold.

## What M1 contains

- Application shell
- Public landing experience
- About, services, and contact routes
- Product catalogue and product detail routes
- Route-specific metadata, canonical handling, robots, and sitemap behavior
- Baseline accessibility and responsive behavior

## What the current M1 work taught

The M1 work in this repo is intentionally route-driven:

- Shared route UI lives in reusable components.
- Page files stay small and expressive.
- Metadata lives with the route.
- The shell stays consistent across all public pages.

This structure makes the public routes easier to extend without copying layout logic into every page.

## Why the code is structured this way

- `ApplicationShell` wraps the public experience so header, footer, and layout logic do not drift.
- Breadcrumbs are shared because navigation context should behave the same on every public route.
- Shared route styles reduce one-off visual decisions.
- Page-level modules keep each page readable while still allowing page-specific visual emphasis.

## How to extend M1 safely

1. Check whether a reusable pattern already exists.
2. Add to the shared component before cloning markup.
3. Keep the route metadata aligned with the page intent.
4. Verify responsive behavior at mobile and desktop widths.
5. Record the result in the issue thread and the docs.

## What not to do

- Do not invent product claims that are not already supported.
- Do not add service-role logic to public pages.
- Do not duplicate breadcrumbs, shell chrome, or metadata behavior in each route.
- Do not treat preview behavior as production behavior.
