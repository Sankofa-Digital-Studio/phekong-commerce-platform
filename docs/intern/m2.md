# M2 Intern Guide

M2 covers the visual-foundation reset, authentication boundaries, and service bookings. Payments, cart and order transactions are deferred to M3.

## Why M2 is sensitive

Booking flows become expensive to fix if the visual system, data contracts, availability rules, and user expectations are not aligned early. M2 therefore starts with one coherent luxury African wellness direction with restrained premium botanical accents.

## Core M2 principles

- Reuse existing components before building a new one.
- Define the data contract before the UI expects it.
- Keep auth explicit and payments out of M2.
- Preserve responsive and accessible behavior in every flow.
- Treat verification as part of the task, not a final optional step.

## How to work M2 efficiently

1. Inspect what already exists in `dev`.
2. Identify the smallest bundle that shares a UI/data contract.
3. Critic the bundle before changing it.
4. Improve only the parts that are weak or inconsistent.
5. Verify the bundle in isolation.
6. Update the issue thread with what changed and what remains.

## Design system and Storybook expectations

- Update tokens only when the new flow needs them.
- Prefer reusable primitives over custom page-only widgets.
- Add or refine Storybook stories when a new interaction pattern becomes reusable.
- Keep states explicit: default, loading, empty, error, success, disabled.

## What to document while implementing M2

- Why the flow is split the way it is
- Which parts are shared
- Which parts are intentionally not shared
- Which backend assumptions are required
- Which issues were bundled together and why

## Anti-patterns

- Duplicating booking UI in multiple pages
- Hiding auth assumptions inside page components
- Styling a one-off page instead of improving the shared token or component
- Shipping a flow without a clear verification step
- Adding cart, order, gateway or webhook scope back into M2
