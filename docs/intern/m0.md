# M0 Intern Guide

M0 is the project guardrail milestone. It exists so later work is safe, reviewable, and repeatable.

## What M0 established

- Repository ownership and access boundaries
- Default branch and branch protection expectations
- Labels, milestones, and issue workflow structure
- Documentation skeleton and verification habits

## Why this matters

Every later milestone depends on M0 being stable. If M0 is loose, M1 and M2 become harder to review because there is no consistent operating baseline.

## What to preserve

- Keep repository metadata and permissions intentional.
- Do not bypass review or protection rules for convenience.
- Keep environment variables explicit and documented.
- Keep the issue tracker readable for humans and bots.

## How to work in M0-related areas

1. Verify the current repo rule before changing it.
2. Document the reason for the change.
3. Keep changes small and reversible.
4. Confirm the repo still follows the access and workflow model afterward.

## Common mistakes

- Editing workflow defaults without understanding the impact on downstream milestones
- Creating undocumented local-only assumptions
- Introducing new conventions without updating the docs
